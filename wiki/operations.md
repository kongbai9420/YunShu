# 运维操作

> 本页的功能会**向真实设备发送命令**。所有设备适配目前只用模拟设备验证过；第一次使用请在测试设备上演练，并在现场或 BMC 页面观察实际效果。

“运维操作”页面有这些标签：电源控制、风扇与温控、温控策略、开启 SNMP、操作记录、控制归属。

## 控制归属

为了防止新旧两套系统同时控制同一台设备，所有控制功能**默认归“旧版控制器”**，新平台不发送任何写命令。即使你从没用过旧版，也要先切换归属，控制按钮才可用。

管理员在“运维操作 → 控制归属”切换：

1. 查看切换前检查，逐项确认（例如旧版服务已停止、旧版里风扇都已切回自动温控）。
2. 输入确认语“切换到新平台”。没有未完成的控制操作时才能切换。
3. 设置了 `YUNSHU_LEGACY_URL` 时，还会确认旧版服务已停止响应。
4. 需要时可以随时“切回旧控制器”：新平台立即停止下发，排队中的操作执行前会被拒绝。

部署设置 `YUNSHU_CONTROL_CUTOVER=0` 时只能查看检查结果，不能切到新平台（切回不受影响）。

## 所有控制操作的共同规则

- 高风险操作要**输入确认语**（设备名称）并填写原因，原因写进审计日志。
- 每个操作**只执行一次**：命令发出前失败记为“失败”；发出后超时或连接中断记为“结果不确定”，**不会自动重试**，并锁定这台设备。必须有人到设备或 BMC 上核对实际状态，在页面上写下核对结果并“确认解除”，才能再操作。
- 执行后再查一次状态，读到预期结果才算“已查询确认”。
- 只使用用途为“控制”或“管理”的端点；同一 BMC 同一时刻只执行一个操作，控制优先于采集。
- 入队时和执行前都按发起人**当前**的角色与资产范围复核权限，全部写入审计。
- 资产必须是“在用”状态。

## 电源控制（IPMI）

| 操作 | 风险 | 结果确认 |
| --- | --- | --- |
| 开机 | 低 | 执行后查询电源状态，确认已开 |
| 正常软关机 | 高 | 请求操作系统关机，可能需要几分钟 |
| 硬件重启 | 高 | 无法从电源状态确认，显示“无法确认” |
| 强制断电 | 高 | 相当于拔电源，可能导致数据丢失 |

资源全景的卡片上也有“电源操作”快捷入口，会先显示核对信息和承载影响（上面跑着哪些虚拟机）。

## 风扇与温控

| 功能 | 说明 |
| --- | --- |
| 恢复原厂自动 | 交给 BMC 按温度自动调速 |
| 固定转速 | 风扇固定一个百分比（0–100 的整数）；低于机型安全下限会被拒绝，不会自动调整 |
| 温控策略 | 为单台服务器选择：原厂自动、固定转速或按曲线；添加后默认停用，确认参数后再启用 |
| 温控曲线 | 若干“温度 → 转速”节点，中间按直线插值。**最后一个节点的温度是熔断温度**（默认 82 ℃）：达到后自动恢复原厂温控，降到熔断温度减回差以下才恢复按曲线调速 |

- 只有机型和固件在能力目录中、确认可以安全控制的服务器才能添加温控策略。
- 温度数据过期、缺失或达到熔断温度时，自动恢复原厂温控，不会降速。

## 虚拟机与容器的电源（默认关闭）

虚拟机和容器通过**发现它的虚拟化平台**（Proxmox VE 或 vSphere）开关机，不使用宿主的 IPMI。

开启条件（按钮旁会写明缺哪一项）：

1. 部署设置 `YUNSHU_GUEST_POWER=1`。
2. 控制归属已切到新平台。
3. 虚拟机资产为“在用”（从虚拟化发现新建的资产默认是“规划中”）。
4. 在 PVE / vCenter 端点所属的资产上，为**同一地址**再加一个用途为“控制”的端点，关联有电源管理权限的凭据（PVE 令牌需要 `VM.PowerMgmt`）。原来的“监控”端点继续用于只读采集。

| 操作 | 说明 |
| --- | --- |
| 开机 | 已经是开机状态时不发送命令 |
| 正常关机 | 需要虚拟机里有客户机工具（PVE 的 QEMU Guest Agent 或 ACPI、VMware Tools）。失败时**不会自动改成强制断电** |
| 强制断电 | 相当于拔电源 |
| 重启 | 无法从电源状态确认 |

### 关宿主前先关其上的虚拟机

对宿主执行正常软关机、硬件重启或强制断电时，确认框里会出现“先正常关闭其上 N 台虚拟机”（默认勾选）和最长等待时间（默认 300 秒）：

1. 先对每台已确认承载的虚拟机发起正常关机。
2. 等全部结束；**全部确认关闭后才发送宿主命令**。
3. 任何一台失败、超时或被拒绝，宿主操作取消，不发送任何宿主命令。

只处理已确认承载关系的虚拟机。关系不完整时，宿主上的其他虚拟机仍会随宿主一起被关掉，请先在“总览 → 资源全景 → 虚拟资源发现与关联”里核对。这一功能也需要 `YUNSHU_GUEST_POWER=1`。

## 在 BMC 上开启 SNMP 与推送（默认关闭）

“运维操作 → 开启 SNMP”通过 Redfish 修改服务器 BMC 的设置，省去逐台登录 BMC 页面：

| 操作 | 作用 | 额外要求 |
| --- | --- | --- |
| 开启 / 关闭 SNMP | 打开 BMC 的 SNMP 代理，以只读方式追加团体名（不覆盖已在用的）；SNMPv3 需要 BMC 上已有同名用户 | 无 |
| 配置 / 移除 Trap 目标 | 让 BMC 把 SNMP Trap 发到平台 | `YUNSHU_SNMP_TRAP=1`、`YUNSHU_SNMP_TRAP_TARGET`，凭据须是团体名 |
| 订阅 / 取消 Redfish 事件 | 在 BMC 上建立指向平台的事件订阅 | `YUNSHU_BMC_EVENTS_URL`（https 开头） |

门禁：

- 部署设置 **`YUNSHU_BMC_SNMP=1`** 才可用；**只有管理员**能执行。
- 控制归属已切到新平台、资产为“在用”、有用途为“控制 / 管理”的 Redfish 端点和凭据。
- 与电源控制共用同一套规则：只执行一次、“结果不确定”锁定、审计。关闭 SNMP 属于高风险，需要输入资产名称确认。

说明：

- 开启后平台用所选 SNMP 凭据读一次设备，读到才记“已查询确认”，并在资产上自动补一个用途为“监控”的 SNMP 端点。
- 读不到 BMC 的 SNMP 设置时（部分品牌使用私有扩展）直接拒绝，不写任何东西。HPE iLO 修改后要重启管理芯片才生效，平台不会自动重启，结果记“指令已接受（未确认）”。
- Trap 目标：Dell iDRAC 使用空闲的告警目标槽位，全被占用时拒绝，不覆盖别人的；按 Redfish 标准支持 SNMP 订阅的 BMC 建订阅；其他品牌会提示手动设置。
- 接收端的部署设置见 [设备接入](devices.md) 和 [配置项参考](configuration.md)。

## 操作记录

“运维操作 → 操作记录”列出全部控制操作：谁、何时、对哪台设备、什么操作、原因、结果：

| 结果 | 含义 |
| --- | --- |
| 排队中 / 执行中 | 还没结束 |
| 已查询确认 | 执行后查到了预期状态 |
| 指令已接受（未确认） | 设备接受了命令，但还没查到预期状态 |
| 已接受，无法确认 | 设备接受了命令，但这种操作无法从状态确认（如重启） |
| 失败 | 命令发出前就失败了，设备没有收到 |
| 结果不确定 | 命令发出后超时或中断，设备可能已执行；锁定该设备，需人工核对 |
| 已拒绝（未发送） | 门禁、权限或条件不满足，没有发送命令 |
| 已取消 | 操作在发送命令前被取消 |

高风险操作的确认语：单台为资产名称，多台为“N 台”。审计与控制操作记录默认保留 365 天（`YUNSHU_AUDIT_RETENTION_DAYS`）。
